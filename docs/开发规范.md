# 开发规范

本文件是项目持续开发规则的唯一维护位置。每个需求在开始分析、修改、验证和交付前，都必须读取并遵守本规范，再按影响范围读取架构和测试资料。

## 规范的适用与变更

1. 普通需求、问题反馈、讨论、建议、进度回复和单次授权只用于当前任务，不自动成为长期开发规则。
2. 只有用户明确命令新增、修改或删除开发规范时，才修改本文件中的规则；不能自行把对话原文、推断出的偏好或一次执行方式写入规范。
3. 用户当前任务的明确指令优先用于该任务。临时限制或例外不自动改写规范，也不延续为以后任务的授权。
4. 架构、测试指南和后续计划记录实现事实、验证方法与候选工作，不承担新增规则的作用。不能通过修改这些资料或 AGENTS.md 绕过规范的变更条件。
5. 历史记录、旧方案和待办条目不是当前开发授权，也不能取代本规范。只有明确的规范变更任务才更新规则；整理时保留既有要求，合并重复项并移出任务历史。

## 每个需求的执行流程

1. 读取本规范，检查当前分支、工作区改动、相关模块及文档，保留用户已有修改。
2. 说明本次范围、预计工作量和必要检查。先处理已确认的问题，小批次实施；不因旧建议或相邻代码自行扩展功能。
3. 明确触发条件、预期行为、影响范围与完成标准，先确定模块和接口归属，再修改代码。
4. 按实际改动选择验证：功能修改执行相关测试；共享层覆盖实际受影响模块；纯文档仅检查内容、链接与差异。
5. 更新使用说明、实现资料、测试步骤和交付记录，提交推送 main，再合并同步 mind。普通需求不修改开发规范。
6. 交付时说明改动、实际检查结果和未验证边界；不能把源码编译、打包成功、模拟测试或历史结果当作本次安装与真实运行验证。

## 架构与代码组织

- 先维护模块架构。每种文件类型放在 `src/modules/<type>/`，通过 `index.ts` 注册，`index.vue` 为入口；解析、样式、格式组件和测试属于模块内部。
- 跨格式组件放在 `src/components/`，公共交互放在 `src/composables/`，共用契约放在 `shared/`，主进程能力放在 `electron/`。
- App.vue 只组织公共入口、窗口和状态，不写格式解析分支；模块不互相引用解析实现。
- 可用 TypeScript 的源码、主进程、构建工具和测试均使用 TypeScript，生成的 JavaScript 不提交。
- 公共能力复用既有组件与契约，不为统一外观添加没有实际能力的按钮，不重复维护同一套实现。
- 异步读取、解析和渲染处理取消、代次、所有权与释放；关闭、隐藏、卸载和失败后清理监听、计时器、Worker、画布及对象 URL。
- 编辑操作先完整验证再一次提交，失败或取消保留原内容；保持撤销、保存检查点、标签卸载及窗口移交一致。
- 当前模块、生命周期和设计资料见 [架构说明](架构.md)；实现参数随实际代码维护，不从普通对话生成长期约束。

## 文件隐私与安全

- 预览文件在本机处理，不上传，不修改打开的源文件，不自动保存预览副本、转换产物、历史路径或最近文件。
- 只持久化用户明确选择的应用设置。密码、查询、批注、编辑草稿和文件引用保持在内存会话中；用户主动另存的副本、导出文件和更新缓存按对应功能边界处理。
- 另存和导出不能覆盖打开的源文件；校验源路径及别名，取消或失败不写入部分结果。
- 保持 sandbox、contextIsolation、IPC 来源和文件所有权检查，以及受控网络与外链访问；不执行文档中的脚本、公式代码或主动内容。
- 资源限制须有实际计费、拒绝和释放行为；不能把局部缓存或画布预算称为整个应用的硬内存上限。
- 不提交依赖、安装包、截图、临时样例、用户文件、凭据或敏感信息；第三方依赖和样例保留必要许可说明。

## 验证范围与测试维护

- 仅在 main 验证本次新增或优化功能及其实际影响范围。mind 仅合并同步，不编译、运行或测试。
- 开始验证前读取 [测试指南](测试指南.md)，按影响矩阵和具体行为选专项；不无依据全量回归，也不为了减少工作量省略必要检查。
- 合并独立读取，避免重复构建与重复测试。产品源码改变后重建相关运行资源；运行资源对应当前源码时才使用 `--skip-build`。
- 纯文档或注释整理只检查内容、链接和差异，不启动应用专项。
- 仅移动或合并测试且断言语义不变时，检查引用、编译测试入口和执行迁移单测；不重建产品资源或启动整组界面回归。改变交互断言时按对应行为验证。
- 测试步骤、样例、断言和覆盖边界随实现维护。有效断言不因文件小、名称相似或间接导入而删除；格式测试归模块，公共测试归 tests/。
- 使用独立测试偏好和无敏感信息的最小样例，不改真实用户配置；前后核对源样例 SHA256。原生对话框、剪贴板和打印出口需要模拟时，说明覆盖限制。
- 类型检查、运行时编译和行为验证分别说明；某次跳过类型检查不写成永久禁令。实体打印、真实安装或升级只在当前任务有明确授权时执行。
- 已通过的检查不重复扩大执行；只有新修改、失败或未解决问题才补充必要验证。不能降低断言或阈值来获得通过结果。

## 分支、提交与同步

- 日常开发和当前工作区使用 main，完成相关检查后提交并推送 origin/main，再运行 `npm run sync:mind` 合并并推送 mind；完成后保持 main。
- 提交仅包含本次需求的代码与文档。保留无关、未授权或已有的未提交内容，不为匹配交接摘要覆盖工作区。
- 公共业务在 main 维护，同步保留分支既有差异；不强制推送，不用整文件覆盖代替冲突处理。
- 同步在独立临时 Git worktree 中完成，不移动、stash 或丢弃当前工作区改动；本地与远端 main、mind 引用先保持一致，mind 不被其他工作区占用。
- 保留同步脚本的合并安全保护与分支校验。冲突或校验失败保留现场，处理时保留双方改动；同步所需 worktree 不用于 mind 功能验证。
- 修改同步脚本时可在 main 用本地样例仓库验证合并保护；普通业务改动不额外发起同步专项。

## 打包、发布与安装

- 打包、发布、卸载、安装及实体打印分别以当前任务的明确授权为依据；一次授权不自动覆盖其他操作或未来任务。
- 版本只从 main 打包并发布，mind 仅同步源码，不生成或发布 mind 安装包。
- 普通运行资源编译不等于生成安装包，普通源码提交不代表已安装软件已更新。
- 发布前核对版本、标签、产物、更新元数据和校验清单；不复用失败运行遗留的校验结果，不静默替换已发布且已验证的产物。
- 安装目录、卸载方式和升级路径按当前任务决定，不把某次安装路径或执行顺序写成通用规则；未实际安装或升级时明确注明。
- 构建、产物校验与手工验收操作见 [测试指南](测试指南.md#构建与发布操作参考)。

- 新增或修改功能时同步 README、相关实现与测试资料；普通对话、临时要求和实施结果只按职责记录，不能写入开发规范。
- 不为每次需求新建重复的方案、验收或建议文档。历史结果不能改写成当前结果，过时说明按后续记录或明确链接说明。
- 文档描述通用产品功能，不加入私人称呼、私人功能或用户文件信息。

## 工作方式

- 未经用户要求不使用多代理；不主动查询或报告账户额度，不自动兑换额度重置。仅在用户明确要求查询时读取，账户使用数据不写入仓库。
- 普通反馈不能自动变成新增规范；认为规则需要调整时可以提出建议，用户明确命令变更后才写入本文件。
